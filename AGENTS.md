This is an Expo/React Native mobile application. Prioritize mobile-first patterns, performance, and cross-platform compatibility.

The app ships on **Android, iOS and Web** from one codebase. Anything you write must work on all three unless you are explicitly handling a platform difference.

## Expo has changed — do not trust your training data

Expo ships breaking changes every SDK release. APIs you remember are likely renamed, moved, or removed. Before writing any code that touches an Expo, EAS, or React Native API:

1. Read the major version of the `expo` package in `package.json`.
2. Fetch the matching versioned docs: `https://docs.expo.dev/versions/v<major>.0.0/`
3. For anything else, fetch https://docs.expo.dev/llms.txt — an index of all Expo docs with corrections to common LLM misconceptions. Follow its links to the specific page you need; never answer from memory.

## Project facts (this repo)

- Package manager is **pnpm** (`pnpm-lock.yaml` present). Use `pnpm <script>` / `pnpm exec <tool>`.
- `pnpm-workspace.yaml` pins `nodeLinker: hoisted` (flat `node_modules`). Keep it: Windows Android builds break on pnpm's nested `.pnpm/<pkg>@<hash>` paths (>250-char CMake object paths). After changing that setting, wipe `node_modules` before reinstalling.
- Expo SDK 57, React Native 0.86, React 19, TypeScript ~6 in **strict** mode.
- Lint is **ESLint 9 flat config** (`eslint.config.js`) — do not upgrade to ESLint 10, `eslint-config-expo` is not compatible with it. Keep the `ignores` list in its **own** config object: mixed into an object with `rules`, flat config scopes it to that object instead of applying it globally.
- Routes live in **`app/`** (not `src/app/`). There is no `src/` directory.
- Native `ios/` and `android/` directories do not exist (Continuous Native Generation) — see *Building with EAS*.
- Local Gradle/CMake builds need **JDK 17**: on JDK 24+ Android Gradle Plugin aborts the native tasks with `WARNING: A restricted method in java.lang.System has been called`. In Android Studio set *Settings → Build, Execution and Deployment → Build Tools → Gradle → Gradle JDK* to 17 (its bundled JBR is often newer, e.g. 25); CLI builds pick it up from `JAVA_HOME`. Leave *Gradle user home* **empty** — a JDK path there puts `wrapper/dists` inside `Program Files` and every sync fails. A successful AS sync writes `android/gradle/gradle-daemon-jvm.properties` with the selected JDK version, and that file also forces the JVM of plain `gradlew` runs (`toolchainVersion=25` reintroduces the CMake failure); delete it or re-sync with the IDE's Gradle JDK at 17.

```bash

pnpm test               # vitest unit tests

pnpm export:web         # production web export
pnpm deploy:rules       # publish firestore.rules to the pinned project
pnpm deploy:indexes     # publish firestore.indexes.json
```

## Code style

- **No semicolons** at end of statements (`semi: never` is enforced by ESLint).
- **No `console.*`** in app code — `no-console` is a warning. Use the error/telemetry paths that already exist.
- **No `any`** — strict TypeScript; define real types in `interfaces/`.
- Keep the `@/` path alias (`@/components`, `@/services`, `@/libs`, …).
- Screens under `app/` export **only** a default component. Any extra component, hook or helper goes in `components/`, `hooks/`, `libs/` or `services/`.
- Prefer plain `useState`/`useMemo` over `useRef(initial).current` when creating non-primitive state (`useState(() => new X())[0]`) — React lint flags the ref form.
- Never mutate a module-level `Animated.Value` across renders; create it once with the lazy `useState` initializer.
- **The React Compiler lint is on and it is strict** (`react-hooks/set-state-in-effect`, `react-hooks/refs`, `react-hooks/immutability`, `react-hooks/preserve-manual-memoization`). Three rules bite in practice:
  - **No synchronous `setState` in an effect body.** A subscription hook that used to `setSnapshot(null)` when the key changed now keeps the key (owner/song) alongside the value and returns `null` while it does not match — derived in render, never synced. A countdown/initial value belongs in its event handler, not in the effect that watches it.
  - **No ref reads (and no functions that close over refs) while rendering.** Building a `PanResponder` with `PanResponder.create({ … ref.current … })` during render fails; the pinch hook returns plain responder props (`onResponderGrant`/`onResponderMove`/…) whose callbacks read the refs only when they fire. If you drop `PanResponder`, keep returning `true` from `onResponderGrant`: that is the only value that blocks the host's native responder on Android (the responder system checks for `true` exactly).
  - **No mutating a value from `useState` or reassigning a closure variable after render.** Keep cross-render mutable bookkeeping in `useRef` and touch it only inside callbacks/effects.

## Navigation & routing

- **Expo Router** for all navigation. Routes live in `app/` — every file is a screen, `_layout.tsx` files define navigators.
- Import `Link`, `router`, `useLocalSearchParams` from `expo-router`.
- The authenticated shell is `app/(app)/_layout.tsx` → `components/app/AppShell.tsx` (sidebar on web/desktop, bottom tabs on mobile). Add new screens to the `Stack` registry there.
- **Modal routes** are registered with `options={{ presentation: "transparentModal", animation: "fade", contentStyle: { backgroundColor: "transparent" } }}` in that same `Stack` and render inside `components/app/ModalScreen.tsx` — a spring-animated panel floating on a translucent backdrop (bottom sheet on phones, dialog on web) instead of `ScreenContainer`. Current modals: `organizations/index`, `organizations/new`, `settings/profile`, `settings/organization`, `members`, `suggestions/index`, `suggestions/new`, `suggestions/[id]`, `setlists/new`, `setlists/[id]/edit`, `performances/new`, `performances/[id]/edit`, `polls/index`, `polls/new`, `polls/[id]`, `songs/[id]/history`. The create/edit forms (`PerformanceForm`, `SetlistForm`, `PollForm`) render `ModalScreen` directly; full-screen editors (`songs/*`) keep `ScreenContainer`.
- **Bottom sheets** are for short option pickers: flip `visible` on `components/ui/BottomSheet.tsx` (`BottomSheet` + `SheetOptionRow`). They slide in from the bottom edge and dismiss by dragging the handle down (or tapping the backdrop). `Dialog`, `BottomSheet` and `ModalScreen` all share `components/ui/SheetSurface.tsx` (translucent backdrop + spring entrance), so never build a new overlay from scratch. The language and theme pickers live in `components/settings/`.
- **Every screen exposes an accessible go-back button** (never rely on the OS gesture alone). `PageHeader` renders it automatically when the router can go back — pass `back` to force it or `back={false}` to hide it — and `ModalScreen` / `AuthLayout` place the same control at the top-left. The label comes from `common.goBack`.
- **Tabs never stack**: the shell is one `Stack`; pressing a tab root runs `goToTab` (`hooks/useTabNavigation.ts`), which collapses the stack to `[Home, currentTab]`, so the native back button from any tab root lands on the dashboard. Tab roots are registered with `animation: "none"` (switching is instant); the anchor is `unstable_settings.anchor = "index"`. `isTabActive` also lights the *More* tab while one of its hosted routes (settings, members, suggestions…) is open.
- **The reader steps through an event's setlist**: opening a song from a setlist screen passes `?setlist=`; only then does the reader show the corner arrows, walking exactly that list (`setlistStep` in `libs/setlistNavigation.ts`). Steps animate by direction through `animationTypeForReplace` (`hooks/useReaderSession.ts`), and stage (fullscreen) mode survives the swap. The general songbook never shows the arrows. Each setlist entry also stores the **key the band will play it in** (chosen when adding a song, editable from the edit-mode row via `SetlistKeyDialog`); the entry syncs live and the reader opens in that key.
- **Live show mode rides that session**: reading from an event's setlist also shows `components/songs/LiveShowBar.tsx` (position, elapsed, the delta against the estimate, next-song peek, break countdown). Its clock lives in `hooks/useReaderSession.ts` (`useLiveShow` + start/stop/break, in memory) so it survives the step to the next song, and the maths is pure in `libs/liveShow.ts` — the **clock** is never written to Firebase (the show *log* is, see the next bullet), and the strip only appears when the setlist really belongs to a performance. **It is a strip, not a panel** (the user asked for the lyrics to dominate): one row of captions plus its icon actions on the reader's own background, ~40pt tall in both modes — there is no `compact` prop any more. The labelled stats block, the estimate and the remaining time are gone on purpose: the delta already says the only thing any of them would change. **The row never carries two numbers at once** — position, then the delta, and the elapsed clock only while the set is on time — which is what keeps `next` from truncating on a narrow phone (hence `position` is the `3/8` form and the delta reads `3:00 late`, not the longer phrasings those keys used to hold).
- **The band logs the show and reviews it afterwards** (roadmap #45): the same session carries a **show log** (`LiveShowSession.log`, one `ShowLogEntry` per song: outcome `played|skipped|improvised`, measured seconds, a note). While a show runs, the reader's mount effect calls `touchShowSong(setlistId, songId)` and its unmount `releaseShowSong(…)` — each arrival closes the previous song's visit (accumulating its seconds, **break windows excluded** through `libs/showLog.ts#visitSeconds`), the strip's third icon (tinted by the mark) opens `components/performances/ShowOutcomeSheet.tsx`, and `startBreak`/`endBreak` bank break windows so a coffee never inflates a song. `stopLiveShow()` closes the visit but **keeps** the log; `startLiveShow(setlistId, { seed, firstSongId })` re-seeds it from the event's stored log. `hooks/useShowLogSync.ts` persists the whole array to `services/performances.ts#saveShowLog` on every change (deduped by payload, fire-and-forget like `logActivity`), so the report opens filled in and a killed app cannot lose the night. The pure core is `libs/showLog.ts` (+18 tests): `sanitizeShowLog` (invalid outcome self-heals as *played*, never skipped — #30's contract), `visitSeconds`, and `buildShowReport`. The **post-gig report** is a plain route `performances/[id]/report` (`components/performances/ShowReport.tsx`, full screen, entry button on the detail once a setlist is attached): one group per attached setlist plus logged songs no list holds anymore, per-row outcome chip → the same sheet, note in a `Dialog`, **write-through** (each mark/note saves the whole log — no draft, so it is deliberately not a focus route and needs no discard guard; mark live during the show, correct here afterwards). **It feeds #34 and #35 through one seam**: `skippedSongIds(log)` — a skipped song counts as never played (`buildSongUsage` leaves no entry, so an older play survives as the last one) and is no year-recap sighting, `improvised` counts as played, and a show with no log keeps every previous behaviour; `musicMinutes` and the recap's minutes deliberately stay on **estimates**, because a visit measures slot time (banter included) — the report is where the two clocks meet. **Writes**: the log is not on `PerformanceInput` (the event form can never clobber it), `firestore.rules`' performance update gains a member carve-out (`showLog`+`updatedAt` only, list ≤ 500 entries; rules cannot iterate, entries are sanitized client-side like annotations' markers) → **needs `pnpm deploy:rules`**.
- **The desktop keyboard drives the reader** (roadmap #8): `hooks/useReaderKeys.web.ts` (native no-op in `.ts`) turns arrows/space/PageUp/PageDown into stepping — Bluetooth page-turner pedals send those same keys — plus up/down transposing, `f` for stage mode, `p` for autoscroll and Escape to leave it. Keys are ignored while a text field has focus or a modifier is held, and the reader mutes them (`enabled`) while a sheet or dialog is open.
- **Wide screens read in two columns** (roadmap #9): the reader passes `columns={isMobile ? 1 : 2}` to `SongContent`, so tablets, desktop and a phone in landscape flow the song across two columns (phones stay single). `balanceColumns` in `libs/songUtils.ts` splits the sections into contiguous, height-balanced groups — a section is never split, order is preserved, and no column is ever started unless the sections left can fill the ones after it. Stage mode uses the same value, so landscape stays intact.
- **Songs carry optional reference links** (roadmap #16): `Song.links` is a `{ youtube, spotify, appleMusic }` map (empty string = unset), edited under the song form's “More details” and rendered by `components/songs/SongLinks.tsx` as one chip per set provider that hands off with `Linking.openURL` — nothing is embedded. `libs/songLinks.ts` is the single validator (bare host → `https://`, unsafe schemes dropped) shared by the editor, the service and the reader, and `links` is whitelisted in `firestore.rules`' song update rule.
- **ChordPro is the interchange format** (roadmap #18): `libs/chordpro.ts` parses/serializes the common subset (`{title|artist|key|capo|comment}`, `{start_of_*}`/`{end_of_*}` sections, inline `[Chord]`s) and round-trips it (a chord past the lyrics is space-padded so its position survives). The song form imports a pasted document (metadata only fills empty fields, replaces the lyrics), and the reader footer exports the song as a `.cho` file through `libs/exportFile`.
- **Paste understands other apps' output** (roadmap #19): `parseLyricBlock` (`libs/songUtils.ts`) turns inline `[C]` chords into the grid (the same `libs/chordLine.ts` helpers as #18), drops metadata headers (`Capo:`, `Tuning:`, `132 bpm`, URLs…) and bare repeat markers (`x2`), normalises non-breaking spaces and collapses blank runs. The editor's paste dialog previews the resulting sections before committing.
- **Ctrl/Cmd+K is the command palette** (roadmap #29, web/desktop only): `components/app/CommandPaletteHost.web.tsx` — native gets a component that renders nothing, `.ts`, so the platform split keeps the DOM listener out of the app bundle. It ranks with `rankSearchable` (`libs/commandPalette.ts`, accent-folding subsequence match with consecutive/word-start bonuses, all unit-tested) over four sources: `SIDEBAR_NAV`, the three “new …” routes, the band's songs (already subscribed, so a query costs no read) and whatever the current screen registered with `usePaletteCommands`. The registry is a module `Map`, not state: commands are only read when the palette opens, so a screen contributes from an effect without re-rendering. The reader registers its transpose that way, showing the key each step lands on. `SheetSurface`'s `placement="center"` is the overlay — never build a second one.
- **The calendar has three views** (roadmap #51): the `month` grid, a `week` strip and an `agenda` from today, all fed by `libs/calendarView.ts` (pure, unit-tested) from one filtered list, so the dots on the grid can never disagree with the lists underneath. The chips filter by **status** — `DEFAULT_STATUSES = scheduled + completed`, cancelled opt-in, and an empty selection snaps back to the default instead of emptying the calendar — with the **event-type group** (`filterByEventType`, #46) one row below. The day button (`components/performances/DayCell.tsx`) and the grid chrome (`calendarStyles.ts`) are shared, so the two grids stay pixel-identical. The week view has **no date of its own**: it anchors on the selected day, its arrows move that selection by a whole week and "Back to today" re-anchors both, so there is no second date to keep in sync. View and statuses are session state — persisting them is #37A's storage shape.
- **Events are gigs or rehearsals** (roadmap #46): `Performance.type: "gig" | "rehearsal"` is **required on `PerformanceInput`** (the #42 omitted-optional trap: an omitted optional would silently turn the band's rehearsals into gigs on the next status tap) and absent on every older document, so `mapPerformance` reads absence back as `gig` and `normalizeInput` re-clamps the value on write — no migration exists. The pure core is `libs/performances.ts` (`EVENT_TYPES`, `DEFAULT_EVENT_TYPES`, `filterByEventType` — empty selection snaps back to the default, exactly `filterByStatus`'s contract — and `isGig`): it feeds the events list's Gig/Rehearsal chip row (the tab counts follow it, and an empty selection renders "no events of those types" instead of the fresh-band copy) and the calendar's second chip group, and **both rows render only once a rehearsal exists** — a control that filters nothing is noise. The form picks the type above the name and relabels its notes field **Goals** for a rehearsal; `PERFORMANCE_TYPE_KEYS` (in `interfaces/performance.ts`) is the one label map — `performances.gig` already means "Event", so the pair needed explicit keys. **Only the exception is badged** (the songbook's own rule): `PerformanceCard`/`PerformanceListRow`, the detail's key facts and the dashboard's next-event hero print "Rehearsal" (`accent` tone), and the cards' accessibility labels say the word. **Counting splits on purpose**: #34's usage history counts every *completed* event (a rehearsal that ran a setlist *was* a play — reader footer, usage filter and #44's rotation stay honest about practice), while #35's show counters (`showsPlayed`, `musicMinutes`, every number of the year recap) narrow to `isGig`. `firestore.rules` accepts `type` on create **when present** (an older client's create without it keeps working) and whitelists it on update → **needs `pnpm deploy:rules`**.
- **Events carry an RSVP and a "who brings what" list** (roadmap #47): `Performance.attendance` is a **map** `{ [uid]: "yes" | "maybe" | "no" }` (absent on older documents = no answers) and the tasks live in the **`performances/{id}/tasks` subcollection** (`EventTask`: `title`, `assignedTo` — uid or `""` = anyone — `done`, `createdBy`, **client-time** stamps so order survives an offline write). The map is deliberately **not** on `PerformanceInput`: the event form and every status tap leave the band's answers untouched, and `setAttendance` writes **one dot-path key per member**, so two answers at once can never clobber each other — the rules pin that a member's event update may only change **their own** key (`diff(...).affectedKeys().hasOnly([request.auth.uid])`), while the admin whitelist carries the whole `attendance` field (map ≤ 100; rules cannot iterate a map, so entries self-heal in `libs/eventLogistics.ts#mapAttendance`, exactly the `markers`/`showLog` precedent). Any member writes tasks — logistics is not an admin job — but `createdBy` is immutable and only its creator or an admin may delete one; the title check is `trim().size() > 0` in the rules (an emulator test caught "  " passing a plain `size()`). The pure core is `libs/eventLogistics.ts` (+9 tests, `partitionAttendance` + `sortTasks` pending-first stable). The detail screen's two cards (`components/performances/AttendanceCard.tsx`, `EventTasksCard.tsx`) **hide for a cancelled event**, tasks subscribe per screen through `hooks/useEventTasks.ts` (band+event-tagged, the #37B shape — the RSVP map already rides the subscribed event), and `deletePerformance` cascades the task list first (Firestore does not cascade subcollections, the `deleteVersions` precedent) → **needs `pnpm deploy:rules`**.
- **The band votes on the date before it books it** (roadmap #48): `organizations/{orgId}/datePolls/{pollId}` (`title`, `options` — 2..10 `{ id, date, time, note }` candidate dates — `status open|closed`, `winningOptionId`, `createdEventId`) with **one availability doc per member** underneath (`votes/{uid}` = `{ optionIds, updatedAt }`, the favorites shape verbatim: owner-only writes, the whole list rewritten each save, doc id = uid, so two votes can never clobber each other and nobody votes for anyone else). The pure core is `libs/datePolls.ts` (+18 tests): `mapPollOptions` (rules cannot iterate a list — the 2..10 shape is pinned there and malformed entries/duplicate ids self-heal here; the canonical order is date → time → id), `toggleOption`/`cleanVoteIds`/`sanitizeVoteOptionIds` (a stored vote cleaned against the poll's own options, so an edited date's orphaned id counts for nothing), `tallyVotes` (a repeated id inside one vote counts once) and **`pollWinner`** — most votes, ties by the **earliest** date, `null` when nobody voted (closing a poll empty-handed invents no night). **Any member proposes** (`polls/new` is a focus route with `useUnsavedChanges` + `DiscardChangesDialog`; the entry is the events toolbar's `PollIcon`, verified against the MCI glyphmap), **only an admin closes and creates the event**: closing stamps `status`/`winningOptionId` through the update whitelist — the winner is computed from the live votes at that moment, never read back — and "Create the event" seeds a scheduled gig from the winner's date/time via `createPerformance` and stamps `createdEventId` back, so nobody books the night twice; `deletePoll` (creator or admin) cascades the votes first (the `deleteVersions` precedent). The list/detail (`polls/index`, `polls/[id]`) are modal routes, votes write-through live, the hooks are band-tagged (`hooks/useDatePolls.ts`, the #37B shape), and the calendar/dashboard stay untouched (the phase's exit criteria) → **needs `pnpm deploy:rules`** (eighth push).
- **Templates are setlists with a flag** (roadmap #41): `Setlist.template` — absent on every older document, so it reads `false` and needs no migration — gives a list the setlists screen's own **Templates** section, rendered first and excluded from "Not attached to an event", because that exclusion *is* the difference between a reusable shelf and a draft nobody has placed yet. **"Save as template" copies instead of converting** (`services/setlists.ts#saveSetlistAsTemplate` writes a *new* document with the date cleared): the running order an event is already using must not be pulled out from under the gig. It asks for a name in a dialog (pre-filled, like the songbook's saved views), and a template offers the way back through `setSetlistTemplate(…, false)`. The grouping lives in pure `libs/setlistGroups.ts` (+11 tests) — never move it back into the screen — and `firestore.rules`' setlist update whitelist carries `template`, so this ships with a rules redeploy.
- **The setlist goal is a slot, break included** (roadmap #42): `Setlist.targetMinutes` + `breakMinutes` (both `0` = no goal, so no migration) with the maths pure in `libs/setlistDuration.ts` (+12 tests) — **the target is the slot and the break eats into it**, so `45/10` holds 35 minutes of music, not 45. `setlistGoal` returns `null` when there is no target: render nothing, never "0m left". `durationGoalText` formats the **absolute** remaining time because `formatDurationLong` maps anything `<= 0` to `"--"` — a signed overrun would print as "… over the goal". The goal row under the running order in `setlists/[id]` recomputes from the stored estimate on every listener echo, so it moves as songs come and go. `SetlistInput.targetMinutes/breakMinutes` are **required, not optional**: the running-order editor rewrites the document through `updateSetlist` and an omitted optional would silently clear the band's goal on the next reorder — and `firestore.rules`' setlist whitelist carries both fields (same redeploy as `template`).
- **Setlists carry dividers and entry notes** (roadmap #43): `Setlist.blocks` (`{ id, name, afterSongId }`) and `SetlistSong.note` (the shared "tune Eb" cue, per entry). **A divider anchors to a song, never to a position** — `afterSongId`, `null` = the top — so a reorder carries every Set/Break/Encore with its music, and *after* (not *before*) is what makes the top, any middle gap **and the space after the last song** reachable. The pure core is `libs/setlistBlocks.ts` (+15 tests): `listRows` interleaves them (song numbers count songs only; a divider whose song left the list renders **after the last song, never hidden**), `removeEntry` re-anchors a removed song's dividers to the gap it filled, `cleanBlocks` is the idempotent hygiene run on map + write. The editor's thin "+" bar above each song (edit mode) opens one dialog with preset chips; dividers get rename/remove but **no move** — the anchor *is* the move. The reader shows the entry's note from `contextSetlist` (any opened list) as an accent wash in normal mode and a conditional second title line in stage mode. `SetlistInput.blocks/songNotes` are **required, not optional** — same trap as the goal fields — notes are keyed by song id like `songKeys` (reorder-safe), the dead `reorderSetlistSongs` was deleted because it would have stripped them, and `firestore.rules`' whitelist carries `blocks` (notes ride inside `songs`).
- **Auth gates**: `app/(auth)/_layout.tsx` bounces signed-in users back into the app (heals the sign-in/redirect race), and `app/index.tsx` only waits for auth — never for the band list, which loads behind the dashboard's own states.
- **Editing flows take over the app**: `isFocusRoute()` in `libs/navigation.ts` lists the create/edit/suggest routes — plus `/onboarding` — and `AppShell` hides the bottom bar/sidebar there, so no stray tap can abandon the work. Every form with unsaved state must additionally call `useUnsavedChanges()` and render `components/app/DiscardChangesDialog.tsx`, so back, Android back, tab presses and browser close ask for confirmation instead of silently losing the draft.
- **Onboarding is offered once**: `app/(app)/onboarding.tsx` (a chrome-hidden route) shows the four welcome slides (`react-native-app-intro-slider`, copy in `libs/onboarding.ts`) and then hands over to `components/onboarding/TourHint.tsx`, which walks the real reader and editor instead of a mock-up. The profile's `onboarded` flag is what gates it: the band-creation and invitation-acceptance flows route here only while it is not `true`, and finishing or skipping stamps it, so an existing account never sees the tour. The reader/editor hints render only when opened with `?tour=reader` / `?tour=editor`, and the admin-only pre-step publishes the sample song (`services/demoSong.ts`) so the tour has real content to play with.
- **Never import `@react-navigation/*`** in app code (SDK 56+): Expo Router ships its own copy, so the app packages were removed from `package.json` on purpose and the bundler errors out if they come back. Import from `expo-router` or, for React Navigation APIs such as `usePreventRemove`, from `expo-router/react-navigation`.

## Firebase

- **Never create a second Firebase config.** `db/firebaseConfig.ts` is the only one. `db/Fire.ts` is the single entry point that re-exports the configured app, auth, storage and path builders.
- **All Firestore access goes through `services/*.ts`**, which use `db/Fire.ts`. Screens never import Firebase directly.
- Batching: use `batch.set(ref, data, { merge: true })`. Rules that must see post-batch state use `getAfter()`, since `get()` sees pre-batch state.
- Web compatibility: `metro.config.js` `resolveRequest` maps `@react-native-firebase/*` and `firebase/auth` to `shims/*.web.ts`. If you add a native-only module, you must add a web shim or guard it with `Platform.OS`. Native modules added outside Firebase follow the same platform split — e.g. `libs/exportFile.ts` (share sheet) pairs with `libs/exportFile.web.ts` (browser download), and `libs/printFile.ts` (`expo-print` → PDF → share) pairs with `libs/printFile.web.ts` (prints a hidden iframe, since `expo-print` on the web can only print the current page). Note `pnpm export:web` is the quickest way to prove a new platform split still bundles.
- Membership is **invitation-only**: `addMemberByEmail` always creates an invitation. Do not reintroduce email→profile lookups — `firestore.rules` deliberately forbids reading other users' profiles.
- **Google sign-in is platform-split**: `services/googleAuth.ts` (native, `@react-native-google-signin/google-signin`) and `services/googleAuth.web.ts` (browser, Firebase popup → redirect fallback). Metro picks `<name>.web.ts` for `platform=web`, so never import a native-only SDK from a shared file — give the platform its own file instead. Android needs `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID` (Firebase Console → Authentication → Google → Web client ID) and the app's SHA-1 registered in Firebase. The native flow tries the ID token from the sign-in response and always falls back to the classic `getTokens()` exchange, so it also works with the access token alone; native Google status codes are decoded in `services/errors.ts` (`GOOGLE_MESSAGES`).
- **Unique usernames live in a public registry**: claiming `usernames/{lowercased name}` is an atomic create (`services/usernames.ts`, `libs/username.ts`), with a `Name-1234` suffix on collision (Google sign-up). Renames are one batch that claims the new key and releases the old one, and the rules enforce one change every 90 days through `usernameChangedAt` + `getAfter`. The profile's `displayName` mirrors the claimed username and is never overwritten from the auth account.
- **Band membership mirrors**: `users/{uid}/organizations/{org}` is each user's private band index. The user writes it when accepting an invitation; admins of that band may only sync the mirrored `role` (or delete the mirror when removing someone) — `services/organizations.ts#syncMemberProfile`/`updateMemberRole`/`removeMember` and `firestore.rules` must stay in step. `hooks/useOrganization.tsx` self-heals the caller's copy (name, email, photo) against their profile, so the members list never shows stale rows.
- **The band list is cache-aware**: `subscribeMyOrganizations` subscribes with `includeMetadataChanges` and a cache-only empty snapshot must never be treated as “no bands”. `hooks/useOrganization.tsx` retries dropped listeners with backoff, shows a retry after a deadline and recovers with a one-shot `getDocsFromServer`.
- **Cold start never blocks on Firestore**: `useAuth` subscribes the profile (cache-first) and backfills `ensureUserProfile` in the background; the splash waits for auth + the first band slice only.
- `firestore.rules` must stay in sync with the write shapes in `services/`. If you change a write, update the rules and re-read `docs/app_implementation.md` §23.
- **The `version` collection gates the native apps**: its `version` field is bumped by hand on each release and `AppUpdateGate` compares it with the installed build (`expo-constants`) — a strictly higher value forces the store update, equal or lower does nothing (`libs/version.ts`). The collection reads publicly so signed-out users update too.
- **Writes are offline-first**: Firestore stores every write in the on-device cache and replays the queue by itself (native persistence is on by default; on web `db/firestoreInstance.web.ts` enables IndexedDB via `persistentLocalCache`). Never bypass `db/Fire.ts`, and never assume a write needs connectivity to succeed.
- Connectivity + queue state live in `services/sync.ts` (`useSyncState()`), rendered only by `components/app/SyncBanner.tsx`. Keep the banner a pure render of that state — do not add connectivity checks (or timers) to screens.

## Firebase rules deploy

- The Firebase project is pinned in `.firebaserc` (`setuno-be01d`); `firebase.json` maps `firestore.rules`, `firestore.indexes.json` and `storage.rules`. Publish with `npx firebase-tools login` (once) then `pnpm deploy:rules`, `pnpm deploy:indexes` and/or `pnpm deploy:storage`.
- `storage.rules` keeps every upload in the caller's own folder under `avatars/{uid}/…` and `organizations/{uid}/…` (see `services/uploads.ts`), images only, under 10 MB. A fresh Storage bucket denies all writes until they are deployed.
- Collection-group queries (invitations) need BOTH the recursive-wildcard rule in `firestore.rules` and the collection-group index in `firestore.indexes.json`; deploy both together with app changes that rely on them.
- The **per-user reader state** (`users/{uid}/readerState/{songId}` — autoscroll speed/delay, the resume point (scroll ratio, transpose, capo) and the per-song text size, roadmap #1/#4/#5) is owner-only and whitelists its fields in `readerStateKeys()` — adding a field there means extending that list *and* redeploying the rules with `pnpm deploy:rules`, or the write is rejected and the setting silently stays local to the session.
- **Private annotations** (`users/{uid}/annotations/{songId}` — free-form `notes` plus inline `markers`) are the same trust model: owner-only, whitelisted by `annotationKeys()`/`validAnnotation()`, never written to the shared song document. Rules cannot iterate the `markers` list, so the document-level shape (types + `2000`/`50` limits) is pinned there and each entry's contents are validated client-side in `libs/annotations.ts#annotationFromData`. Touch either side and redeploy the rules with `pnpm deploy:rules`.
- `firebase deploy --only firestore:indexes` replaces the remote index set with the file, so keep `firestore.indexes.json` up to date before deploying (otherwise unlisted composite indexes are removed).

## Preferences & storage

- Anything the user configures must survive a restart: theme/accent (`services/themeManager.ts`), language (`services/i18next.ts`) and reader settings — font size, chord layout, notation, motion and the stage-mode keep-awake toggle (`services/prefs.ts`).
- The reader also stores `chordNotation` (`"letters" | "solfege" | "nashville"`): chords and keys are always **stored** in american letters, and the reader spells them through `displayChord` / `displayKey` (`libs/chords.ts`). Nashville numbers (1 4 5) are relative to the song's key, so `displayChord` takes the key as a third argument and falls back to letters when it is missing; a key never renames itself. The editor and the chord pad always stay in letters (that is what gets saved).
- **The pad autocompletes and the form validates** (roadmap #21): the chord pad's custom field offers live suggestions (diatonic chords of the key, your recents, `COMMON_CHORDS`) and refuses anything `isRecognizedChord` rejects. That check is deliberately stricter than `looksLikeChord` — it whitelists quality spellings, so solfège (`Do`), German (`Hm`) and Nashville (`IV`) fail while numeric extensions (`E6/9`) pass. `EditorLine` tints unrecognised chips red, and `SongForm` warns once before saving (`collectSongChords` → dialog with “Save anyway” / “Review”). Nothing is auto-translated: the editor still stores letters.
- **The editor has undo/redo** (roadmap #25): `libs/history.ts` is the pure, tested stack (cap 100; edits within 600 ms coalesce, so a typing burst is one step; a new edit clears the redo queue) and `hooks/useUndoRedo.ts` wraps it in `useState`. `SongForm` routes its `sections` through it, `SongEditor`'s toolbar renders the Undo/Redo buttons, and `hooks/useUndoRedoShortcuts.web.ts` maps Ctrl/Cmd+Z, Ctrl/Cmd+Shift+Z and Ctrl+Y (the native file is a no-op). History is per screen and never persisted.
- **Sections are blocks** (roadmap #27): the type picker (`SECTION_TYPES`) can **insert** a block after any section, a section can be **duplicated** below itself (`duplicateSection` deep-copies lines/chords under a fresh id) and moved up/down, and `SongSection.bars` is an optional bar counter edited through `components/songs/editor/SectionBarsDialog.tsx` (`clampSectionBars` bounds it to 0–999, 0 = unset) and shown next to the section label in `SongContent`. `services/songs.ts` maps and clamps `bars`; the song rules whitelist the whole `sections` field, so no rules change is needed.
- **Creating a song warns about a duplicate** (roadmap #39): `findDuplicateSongs` (`libs/songSearch.ts`, pure, tested in `tests/unit/songSearch.test.ts`) matches the normalised title and narrows by artist — when both the draft and the stored song credit somebody, a different artist is left alone; same-artist rows rank first. `SongForm` runs it on create only (editing never flags itself) and opens a dialog listing the candidates (`SongRow`; tap one to open it instead) beside “Create anyway”, which carries on through the existing unrecognised-chords warning. Taking the existing song disables the leave guard for the transition (`openExisting` state), so abandoning the draft asks nothing extra. Nothing is ever blocked, and `songs` comes from `useOrgData`.
- **Songs duplicate and merge** (roadmap #32): the reader footer's admin actions (beside Delete). **Duplicate** is `services/songs.ts#duplicateSong` — every field copied under a fresh id, section ids kept on purpose (annotations anchored to them stay valid on both songs), the `" (copy)"`/`" (copia)"` suffix passed localized from the screen and bounded by `duplicateSongTitle` (`libs/songMerge.ts`), then straight into the copy's editor. **Merge with…** is `components/songs/MergeSongsDialog.tsx`, one dialog in two phases (pick — `findDuplicateSongs` hits ranked first, tagged "Same title" — then choose which song survives, with the exact counts and the deletion warning).   created in the year; `recapYears`/`defaultRecapYear` open the picker on the latest year with content
  (skipping a future booking). The route is a **modal** (`modalOptions` in the Stack) with a
  `SIDEBAR_NAV`/`MORE_NAV` `StatsIcon` entry; the card
  (`components/stats/YearRecapCard.tsx`) carries **no remote images** so capture never waits on the
  network. Capture is **one dependency**: `react-native-view-shot` (SDK 57 docs list it as
  third-party *with web support* — html2canvas ships inside it), wrapped by the `libs/shareImage.ts` /
  `.web.ts` seam — native writes a `tmpfile` into `expo-sharing`, web captures a **`data-uri`** (never
  `tmpfile`: that path logs the library's warning) and downloads the PNG like `exportTextFile`. **No
  schema, no rules change — nothing to deploy.**
- **Songs and setlists print to PDF** (roadmap #20): `libs/songPrint.ts` is a **pure** HTML builder — no React, no DOM, no `expo-print` — so the whole sheet is unit-tested in `tests/unit/songPrint.test.ts`. It reuses `buildChordRow`, so the printed page is the exact character grid the reader draws (chord row over the lyric line), and its CSS carries `white-space: pre-wrap` — **never let the grid fall back to normal HTML whitespace**, every column would collapse. Chord-only lines (intro/riff) print as the progression, lyrics-only mode drops them, section labels go through `t`, and a setlist is printed **in the key each entry stores** via `semitonesBetweenKeys` + `transposeSections` (entries carry only `key`, never capo). Options: with/without chords + small/normal/large. `components/songs/PrintSheet.tsx` is the shared picker, used by the reader footer and the setlist overflow menu; the pure builders take `t` as an argument, so the sheet stays localized without importing i18next. The grid uses a **system** monospace stack — iOS printing renders in a `WKWebView` that cannot load a bundled font.
- The reader shows the song in one of three layouts (`chordView: "both" | "lyrics" | "chords"`, #6): chords above the lyrics, lyrics only, or a chords-only chart (each line's chords laid out as pills instead of the monospace grid).
- The theme mode is `"dark" | "light" | "system"` (`interfaces/user.ts`, `libs/appearance.ts`). `"system"` is collapsed by `resolveAppearanceMode()` and `hydrateAppearance()` subscribes to OS colour-scheme changes, so the palette follows the device without rewriting the stored preference.
- All of them are hydrated together in `app/_layout.tsx`'s `Promise.all` before the first frame (the same list also restores recent chords and the songbook's saved filters/sort — **adding a storage read means adding it there**, or the screen that needs it reads empty on its first render), so nothing flashes with default values.
- `services/users.ts` mirrors the profile's `preferences` into the local cache (and back), so settings are available offline and before the profile loads. Writes are local first, then Firestore.

## Design system & UI

- `constants/Theme.ts` is the token source (colors, spacing `xxs, xs, s, m, l, xl, xxl, xxxl, huge`, radii `xs, s, m, lg, xl, xxl, pill`, typography). Note the keys are `s`/`m`/`l` — **not** `sm`/`md`/`lg`.
- The palette is derived, never hand-written per screen: `services/themeManager.ts` tints the dark surfaces towards the active accent, and in light mode it darkens the accent (flipping `onPrimary` to white) so text/icons keep AA contrast. Resolve colours **inside** components/factories (`Theme.colors[...]` at render or in `createStyles`) — never capture them in module-level constants, or the value goes stale on theme switch.
- Build styles with `useThemedStyles<T>(factory)`; the factory receives the palette version so style memoization invalidates correctly.
- Reuse `components/ui/` primitives before writing new ones: `AppText`, `Button`, `Input`, `Card`, `Dialog`, `BottomSheet`, `Toast`, `States`, `PageHeader`, `Avatar`, `Icons`, `DateField`.
- Use `Dialog` for confirmations, `BottomSheet` for short option lists, and `ModalScreen` for screens presented as modals. Destructive actions always ask for confirmation. A dialog whose body brings its own scrolling list must pass `bodyScroll={false}` (nesting a virtualized list inside the body ScrollView warns and stacks two scrollers).
- **The toast anchors above the real bottom chrome**: `hooks/useBottomChrome.ts` measures the bar + banner and `components/ui/Toast.tsx` sits 12 points above it (or near the bottom edge when there is no chrome). `pointerEvents` is only ever declared in `style` (a unit test bans the prop, react-native-web deprecation), and the overlay is `box-none` so its controls stay tappable. Every native `Modal` (`Dialog`, `SheetSurface`, the band switcher) also mounts `ToastOverlay`, so a notification is never hidden behind an open modal.
- **Haptics** live in `libs/haptics.ts` (`expo-haptics`, fire-and-forget, no-op where unsupported): tab switches tick, buttons tap, toasts confirm or buzz on error.
- **The chord/lyric grids are monospaced and bundled**: `Theme.fonts.mono` points at JetBrains Mono, registered with per-weight deep imports in `app/_layout.tsx` (importing from the package root bundles all 27 weights). Never set `fontWeight` on a mono grid row — Android can fall back to a proportional face and every padded column drifts. `buildChordSegments` keeps the exact grid while making each chord tappable and tags every chord segment with its `position` (the offset a suggestion stores for a chord change, which is what lets `libs/songDiff.ts` mark the one chord that moves without re-deriving the padding); `buildChordRow` is its joined text.
- **Diffs are struck-through danger plus an accent wash** (roadmap #54): `libs/songDiff.ts` is pure and reusable — `diffWords` is a word-level LCS diff (whitespace is its own token, runs are coalesced, and past `DIFF_TOKEN_LIMIT` tokens it gives up and reports the whole text removed then added rather than building a quadratic table), `diffChordLine` marks the single chord that moves by rebuilding the row with the proposal in place, and the chord that is there **now** wins over whatever the suggestion claimed. `components/ui/DiffText.tsx` renders the runs: the outer `AppText` owns the type scale and the spans are plain `Text`, and the line carries an accessibility label spelling both sides out, because a screen reader otherwise hears the two spellings with nothing to say which is which. Roadmap #26's version history is meant to reuse both halves — never write a second diff.
- On Android, an element whose rounded background appears only in a different state can paint square: keep a background defined from the start (`BottomBar`'s `tabIcon` is transparent until active) and remount the view when the state flips.
- **Do not use `@react-native-community/datetimepicker` directly** — use `components/ui/DateField`.
- Clipboard: `import * as Clipboard from "expo-clipboard"`.
- Every list needs loading / empty / error states, and every destructive action needs a confirmation `Dialog`.

## Reader & chord shapes

- The reader (`app/(app)/songs/[id]/index.tsx`) keeps its display state in preferences: the chord layout (`chordView`), the notation (letters / solfège / Nashville numbers) and the preferred **instrument** (`chordInstrument: "guitar" | "ukulele" | "bass" | "piano"`). Stage mode is per session, and text size, transposition (`semitones`) and capo are remembered per song and per user (see below).
- **The reader's controls live in a bottom tray, not above the lyrics** (`components/songs/ReaderDock.tsx`): the header keeps only the title, back and edit — stage mode has its own button in the tray, so a second one up there was only one more thing in the way — and `SongControls` + `AutoscrollBar` render inside a tray pinned to the screen's bottom edge — the artist moved down to the details line so the header is a single row. Shut it costs one `READER_DOCK_HEIGHT` row (46 — the scroll's bottom padding and the corner arrows' `bottomOffset` both key off it): autoscroll transport, the tuning summary (tap it to open the panel), stage mode and the expand chevron, with a 2px autoscroll progress hairline on its leading edge. Open it grows upward over the lyrics with the full controls, so the lyrics start at the top of the screen instead of a third of the way down. `AppShell` already leaves the screen above the tab bar + banner, so `bottom: 0` needs no chrome arithmetic. **Render order matters**: the setlist corner arrows are painted *before* the tray, so the tray is what sits on top of them — with the panel open it grows over the arrows and hides them instead of leaving them floating above the controls (later siblings paint over earlier ones on Android).
- **The tray is chrome, not a card**: it shares the tab bar's `Theme.colors.chrome` surface and is separated from the song by one hairline — no radius, no shadow, no border. It deliberately does *not* look like a floating box over the lyrics. For the same reason `SongControls` and `AutoscrollBar` no longer paint a `background` or their own rules: they are transparent panels inside the tray, which owns the surface and the divider. The panel's height and the chevron's turn are driven by **one** `Animated.Value` (`useNativeDriver: false`, because height cannot be native-driven), it stays mounted and clipped to `0` when shut (so its height is known before the first tap) and is hidden from touch and the a11y tree (`pointerEvents` in `style`, `accessibilityElementsHidden` + `importantForAccessibility` + `aria-hidden`); stage mode's bar springs in on entry.
- **Tapping the song body toggles the presentation layer**: with the tray open the tap closes the tray — that tap was aimed at dismissing the controls, not at going fullscreen — and otherwise it enters *or leaves* stage mode, symmetric. Both bodies are a `Pressable` with `accessible={false}` (chords and markers keep their own focus and win the responder negotiation), ignored while the reader tour is open and while that same tap just paused a running autoscroll — the first tap stops the scroll, the second does the mode change. Stage mode's exits are that tap or the icon in the stage bar (which carries the title + key, the transport and keep-awake); the display-title block is gone, so a song starts at its first line.
- **Autoscroll is per user and per song**: speed (lyric lines per minute) and start delay live in `users/{uid}/readerState/{songId}` (`services/readerState.ts` + `hooks/useReaderState.ts`, owner-only rules), so they sync across devices while the shared song document is never touched. The transport is per session: `hooks/useAutoscroll.ts` glides the `ScrollView` with `requestAnimationFrame` (discrete one-line steps when `reduceMotion` is on), pauses on a manual touch or drag, and the same button resumes from where the reader left off. The speed/delay controls reset with the song, and the bar (`components/songs/AutoscrollBar.tsx`) renders inside the reader's bottom tray alongside `SongControls` (see above) — stage mode only carries the single transport chip, because the immersive bar has no room for more. Its readout comes from `autoscrollStatusText` in `libs/autoscroll.ts`, so the bar and anything else quoting the transport can never disagree.
- **The metronome practises at the song's tempo** (roadmap #11): the dock icon (lit while a run is going) opens `components/songs/MetronomeSheet.tsx` — bar size, downbeat accent, count-in, ±1 BPM and tap tempo — while the transport lives in `hooks/useMetronome.ts` and dies with the screen, so closing the sheet never stops the clicks. The BPM **derives** from `song.bpm` until the user edits it (`manualBpm`), never seeded once in state, so a song that finishes loading after the screen mounted still opens the right tempo. Timing is pure and tested in `libs/metronome.ts` (+24 tests): every beat is computed from an **anchor**, never incremented (a stalled JS thread delays a tick but can never drag the tempo), a beat overdue past half a beat is skipped instead of fired as a burst, a tempo change re-anchors so the last fired beat keeps its place, and tap tempo is a trimmed mean that breaks its run at a pause. `libs/metronomeEngine.ts` drives it with a 25 ms tick + lookahead and **one file for every platform** (`expo-audio` ships a web build — deliberately no `.web.ts` split, so both platforms share one timing path); the clicks are two ~2 kB generated WAVs (`assets/metronome/`, module-singleton players), the accent is a fifth up at full volume plus a firmer haptic, and the `expo-audio` plugin in `app.config.js` keeps `enableBackgroundPlayback: false` — no foreground service for a tool that stops when the app leaves the foreground. **Section loops ride that same transport** (roadmap #15): `startLoop`/`loop`/`loopView` in `useMetronome` play a count-in bar and the tapped section's `bars` forever, and the loop is **phase over `beat.index`** (`sectionLoopView`, `libs/sectionLoop.ts`, pure, +9 tests) — the engine never restarts, so nothing can drift and a tempo re-anchor cannot move the loop; `stop` ends a loop and a plain run alike because there is one transport. Tapping a section's header (`SongContent`'s heading is a `Pressable` when the reader wires `onSectionPress`, washed in the accent while its loop plays) opens `components/songs/SectionLoopSheet.tsx`, which needs the section's `bars` (>0) — without them it points at the editor instead of faking a length.
- **The tuner is a shipped feature** (roadmap #13, hardware-validated by the owner — "prácticamente perfecto" was the item's ship condition): `/tuner` with a `TunerIcon` (`tuning-fork`) entry in `SIDEBAR_NAV`/`MORE_NAV`, not a focus route. The verdict memo is `docs/tuner_spike_memo.md` — **JS DSP is sufficient**, no native module. `expo-audio`'s `useAudioStream` streams float32 PCM to the JS thread in ~100 ms chunks on both natives, but its **web build is a stub** (`stream: null` in 57.0.5), so the mic has a platform seam: `hooks/useTunerStream.ts` (expo-audio) / `.web.ts` (`getUserMedia` + `ScriptProcessorNode`, browser processing requested **off** — a de-noised signal is a detuned signal), both behind `interfaces/tuner.ts`. The DSP is pure and tested: `libs/pitchDetection.ts` (YIN — compute the cumulative-mean array **before** searching for the threshold crossing, and descend to the trough's floor; the period refinement fits the **raw** difference function, kept in a `raw` copy beside the normalized one, because the normalization's τ-multiplication and running mean tilt the parabola where τ is only ~18 samples — that is what pins fractional periods under **1.5 cents**; `TUNER_MIN_FREQUENCY = 30` so a 5-string low B tunes) and `libs/tunerEngine.ts` (ring of `TUNER_RING_SAMPLES` = window + a **30 ms onset trim** — the pluck's transient never enters an estimate, since three bad frames would outvote the median's five; decimate at ≥32 kHz, median-of-5, `TUNER_NEEDLE_ALPHA` exponential glide so the needle sweeps instead of stepping, ~6-chunk decay hold), ~2.5 ms per analysis on desktop V8. The readout is plain language, never a bare "24¢": the verdict spells `tuner.sharp_one/_other` ("Sharp — lower it 4 cents"), `tuner.centsHint` defines a cent, the gauge carries ticks every 10 ¢ and a green ±5 ¢ band, the note letter is tinted by state and spelled through **`chordNotation`** (`displayNote`; Nashville without a key falls back to letters by design), entering the band fires `hapticTuned` (`libs/haptics.ts`), and the faint caption labels the device's `analysisMs` (`tuner.budget`). **Native testing needs a dev build** (the mic permission lives in `app.config.js`).
- **The reader remembers where you left off** (roadmap #4): the same document also stores `scrollRatio` (0..1, quantized to 2%), `semitones` and `capo`. `hooks/useReadingPosition.ts` writes the position after the reader stops scrolling (debounced, flushed on the way out) and the reader restores it once, when the saved state *and* the layout are known — a scroll the reader made first always wins (`libs/readerState.ts` clamps every value on read and write). Transpose/capo open from the saved value unless the setlist's chosen key applies, and the `SongControls` refresh button is the one-tap reset (key, capo, position).
- **Text size is per song too** (roadmap #5): `hooks/useFontSizePinch.ts` resizes the lyrics with a two-finger pinch (PanResponder — the app's gesture pattern; single-finger touches are never claimed, so scrolling is untouched) and commits on release, while `hooks/useFontSizeShortcuts.ts` / `.web.ts` map Ctrl/Cmd + `+`/`-` and Ctrl/Cmd + `0` on the desktop. The size lives as `fontSize` in the same `readerState` document and also becomes the profile default, so a song nobody resized opens at the last size chosen; `libs/readerState.ts#clampReaderFontSize`/`pinchFontSize` own the maths and the `13..30` range shared with `SongControls`.
- **Private annotations are per user and per song**: whole-song `notes` and inline `markers` anchored to a `sectionId` + `lineIndex` live in `users/{uid}/annotations/{songId}` (`services/annotations.ts` + `hooks/useAnnotations.ts` + `libs/annotations.ts`). The reader shows each marker as a chip above its line (or the section label) via `SongContent`'s `markers`/`onMarkerPress`, and an end-of-song `components/annotations/AnnotationsBlock.tsx`; both open `components/annotations/AnnotationsForm.tsx` (modal route `app/(app)/annotations/[id].tsx`), which edits the notes and the inline notes with a section→line picker. Anchors are resolved against the live song, so a marker whose line or section disappears falls back to the section (or a "removed" label) instead of breaking rendering — the shared song document is never touched.
- **Tapping a chord opens the “how to play” sheet** (`components/songs/ChordShapeSheet.tsx`), only in the reader (`SongContent` receives `onChordPress`). Guitar and ukulele voicings come from the bundled MIT `chords-db` dataset (`libs/chordShapes.ts`, several positions paged with arrows, one lookup shared by `findFrettedVoicings` — the package ships exactly those two instruments); piano notes and **bass positions** are derived from the chord spelling (roadmap #24, revised after the owner's review): **one position, one dot — the root alone** on a **5-string diagram (B0 E1 A1 D2 G2)**, landed on the lowest sounding position inside the five-fret window with the open string winning when both spell the same pitch (fret 5 on the B string *is* the open E), and a slash chord plays its bass note as the root — no bass dataset exists, so inventing one would mean shipping shapes nobody verified. **Mandolin is deliberately absent**: `chords-db` has no mandolin data and a pick-strummed instrument does not accept the muted inner course a derived triad would need, so a wrong diagram is worse than none. With a capo set, the fretted side shows the shape to finger (displayed chord minus the capo) and labels it; piano shows the written chord. **Slash chords** resolve to the dataset's dedicated `/B` or `m/B` voicing; `findFrettedVoicings` reports `slashApplied`, so a chord whose quality has no slash entry (`G7/B`) — and every ukulele chord, since that dataset carries no slash suffixes at all — falls back to the plain shape and the sheet says so instead of hiding the bass. **Favourite voicings** (roadmap #23): a star in the pager pins the position currently shown — the pin lives in `UserPreferences.voicings` keyed `${instrument}:${chord}` (`voicingPrefKey`) with the shape's stable frets id (`guitarVoicingId`), so the answer never sits on the song and `orderGuitarVoicings` opens the sheet on it; bass derives a single position, so it is never offered a pin.
- **The sheet plays what it shows** (roadmap #14): a play button beside the instrument tabs sounds the voicing on screen — the paged position for guitar/ukulele, the derived one for bass, the piano voicing (capo never applies to it). Sounding pitches are `frettedSoundingMidis` / `bassSoundingMidis` / `pianoSoundingMidis` in `libs/chordShapes.ts`, and the fret rule is the diagram's own: **a fret of `0` is the open string and never moves with `baseFret`** (a high position may still let one ring — 193 guitar positions break under the naive relative shift; a test pins all ~4200 dataset positions against their own `midi`), frets ≥ 1 are relative, the capo adds itself back. The synthesis is pure TS in `libs/chordSynth.ts` — Karplus-Strong for the plucked instruments (damping derived from a constant *time* half-life, so high strings do not die early; the noise-burst excitation is **band-limited in harmonic count** — one partial per 4 Hz of string (`EXCITATION_PARTIAL_HZ`) up to the `EXCITATION_HARMONICS = 20` cap the guitar/ukulele sit at, floor `EXCITATION_CUTOFF_MIN = 200`, and a reduced count (sub-E2) cascades a **third pole at −18 dB/oct** — **and tilted like a real pluck** (`PLUCK_TILT = 2`: one one-pole at twice the note itself, so partials fall ~6 dB/octave from the first ones — a finger or pick displaces the string smoothly, while flat white noise is the "struck with something metal" spectrum; the band limit decides how far up the burst reaches, the tilt decides how the partials fall on the way there) — re-levelled to a fixed RMS (`EXCITATION_RMS`) before it sounds, then each note opens on a **smoothstep** ramp spanning **0.45 of its own period** (`PLUCK_ATTACK_PERIOD_SHARE`, clamped 2…14 ms: ~11 ms at E1 so a bass *swells* like a finger pluck instead of clicking like a slap, 2 ms at C4; the S-curve eases the first samples so the attack has no slope kink to tick with) — a whole chord is a **strum**: strings arrive one `STRUM_SPREAD_SECONDS` (40 ms) behind the other in string order, each with its own deterministic ±25 % of force (`strumVelocities`/`STRUM_VELOCITY_JITTER` — identical velocities made a correctly staggered sweep still read as one event; a lone note and the piano, one gesture struck together, keep equal weight). Full-band noise read as saturation on small speakers, and for a 33 Hz bass note it was also the wrong instrument: white noise gives every partial equal energy, so a note with ~660 partials put 59 % of its energy above 1 kHz and played back as a metallic ping — filtering in *harmonic count*, not Hz, is what makes every pitch open on the same shape) and decaying inharmonic partials for piano — deterministic, peak-limited, end-faded; `libs/wav.ts` is the 16-bit encoder. Playback is the platform seam: `libs/playChord.ts` (WAV to cache + one module-singleton `expo-audio` player, like the metronome) / `.web.ts` (WebAudio `AudioBuffer`, no file); the seams only carry samples — never re-implement synthesis there. The button stops on unmount, close and instrument switch, and is disabled exactly when the chord has nothing to sound.
- The arrow/page controls, the sheet's instrument tabs and the diagrams (`FretboardDiagram`, `PianoChord`) are plain views — no native modules — and every diagram exposes an accessible label.

## Testing

- `vitest.config.mts` defines two projects: `unit` and `integration`. Put pure-logic tests in `tests/unit/`, Firestore-rules tests in `tests/integration/`.
- Tests that would import React Native must read the source file as text instead. The existing guards: `routes.test.ts` (every nav href maps to a route module with a default export), `i18n.test.ts` (locale parity + static keys exist) and `rnwDeprecations.test.ts` (no `pointerEvents` props).
- Integration tests run against the Firebase emulator — see `tests/integration/README.md`. The seed rules suite (`firestoreRules.test.ts` + `storageRules.test.ts`, through `@firebase/rules-unit-testing`) is easiest to run as `npx firebase-tools@latest emulators:exec --only firestore,storage "pnpm test:integration"` — it needs **Java 21+** (the CLI refuses older JVMs; Gradle still wants JDK 17, so point `JAVA_HOME` at Android Studio's bundled JBR for this one). The integration project sets `fileParallelism: false`: the emulator is a single shared data store, never run its files side by side.
- **CI runs the same gates** (`.github/workflows/ci.yml`, roadmap #74): every push to `main` and every PR gets `verify` (typecheck → **`pnpm exec eslint .`** → unit tests), `web` (`pnpm export:web`) and `rules` (the emulator suite above; Node 22, pnpm 12, Java 21). The lint step bypasses `pnpm lint` deliberately — `expo lint` has been known to exit 0 while eslint reports real findings; `pnpm exec eslint .` is the truth-teller. `db/firebaseConfig.ts` is not in git, so CI generates it from placeholder `FIREBASE_*` env vars through `scripts/ensure-firebase-config.mjs` before typechecking — if the config grows, extend that script's variable list **and** the workflow's `env` together.

## Deploying the web (Vercel)

`vercel.json` at the repo root is ready for the static export: it runs
`pnpm export:web`, serves `dist`, adds the SPA rewrite Expo Router needs for
